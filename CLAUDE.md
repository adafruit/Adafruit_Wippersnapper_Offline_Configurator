## Project Overview

This is a web-based configurator for creating and editing `config.json` files for the [Adafruit WipperSnapper Offline Data Logger](https://github.com/adafruit/Adafruit_Wippersnapper_Arduino/tree/offline-mode) firmware. It's a single-page application that runs entirely in the browser and can work offline.

**Live Site**: https://adafruit.github.io/Adafruit_Wippersnapper_Offline_Configurator/

The tool enables users to:
- Select a microcontroller board
- Configure RTC (Real Time Clock) and SD card settings
- Add companion boards (FeatherWings, shields, etc.)
- Select sensors/components for data logging
- Generate a `config.json` file for the firmware

## Architecture

### Core Files (Manual Editing)

These are the primary files you'll edit for UI/functionality changes:

- **`index.html`**: Main HTML structure with embedded CSS styles and UI layout
- **`load-wippersnapper-data.js`**: Data loader and app state manager
  - Loads board/component definitions from `.js` files
  - Manages global `appState` object
  - Manually adds I2C multiplexer components (PCA9546, PCA9548, TCA9546, TCA9548)
  - Initializes UI and attaches event listeners
- **`wippersnapper-config-builder.js`**: Configuration builder logic
  - Contains `companionBoardConfigs` (manually maintained companion board definitions)
  - Handles component selection and pin assignment
  - Generates the final `config.json` output

### Auto-Generated Files (DO NOT EDIT DIRECTLY)

These files are regenerated by Python scripts:

- **`wippersnapper_boards.json/js`**: Board definitions
- **`wippersnapper_components.json/js`**: Component/sensor definitions
- **`firmware-data.js`**: Latest firmware release info and download URLs

### Python Conversion Scripts

- **`convert_all_wippersnapper_definitions.py`**: Master script that orchestrates the entire conversion process
- **`convert_boards_to_json.py`**: Converts board definitions from submodule to JSON/JS
  - Includes custom board definitions for boards without `definition.json` files (e.g., generic-esp32-s2)
- **`convert_components_to_json.py`**: Converts component definitions from submodule to JSON/JS
  - Contains `get_image_from_adafruit_product_url()` to fetch product images from Adafruit API
- **`fetch_latest_release_info_and_assets.py`**: Fetches latest firmware release metadata and .uf2 file links from GitHub

### Submodules (Source Data)

Git submodules provide upstream board/component definitions:
- **`Wippersnapper_Boards/`**: Board definitions (branch: `offline-mode`)
- **`Wippersnapper_Components/`**: Component definitions (branch: `offline-mode`)

These point to separate Adafruit repositories and are updated automatically by CI/CD.

## Common Development Commands

### Setup and Initialization

```shell
# Install Python dependencies
pip install -r requirements.txt

# Initialize/update git submodules
git submodule update --init --recursive

# Force submodules to latest on offline-mode branch
cd Wippersnapper_Boards && git reset --hard origin/offline-mode && cd ..
cd Wippersnapper_Components && git reset --hard origin/offline-mode && cd ..
```

### Regenerate Board/Component/Firmware Data

```shell
# Run the complete conversion process
python convert_all_wippersnapper_definitions.py
```

This will:
1. Convert boards from `Wippersnapper_Boards/boards/` to JSON/JS
2. Convert components from `Wippersnapper_Components/components/` to JSON/JS
3. Fetch latest firmware release info from GitHub
4. Verify/update companion board image URLs from Adafruit product pages
5. Output: `wippersnapper_boards.{json,js}`, `wippersnapper_components.{json,js}`, `firmware-data.js`

### Testing Locally

Open `index.html` directly in a web browser. The app loads data from local `.js` files, so no web server is required.

## Key Architectural Patterns

### Data Flow

1. **Submodules** (Wippersnapper_Boards, Wippersnapper_Components) contain protobuf definitions
2. **Python scripts** convert protobuf → JSON → JavaScript module format
3. **`load-wippersnapper-data.js`** dynamically loads JS modules into `appState`
4. **`wippersnapper-config-builder.js`** uses `appState` data to build UI and generate config

### Companion Boards

Unlike boards and components (auto-generated from submodules), **companion board configurations are manually maintained** in `wippersnapper-config-builder.js` in the `companionBoardConfigs` object. Each entry defines:
- `rtc`: RTC chip type (e.g., 'PCF8523', 'DS3231', or null)
- `sdCardCS`: SD card chip select pin (or null)
- `extras`: Additional features description
- `productURL`: Adafruit/vendor product page
- `documentationURL`: Learn guide URL
- `image`: Product image URL (auto-verified/updated by conversion script)

Examples include: Adalogger FeatherWing, PiCowbell Adalogger, Data Logging Shield, Audio BFF, etc.

### I2C Multiplexers

I2C multiplexers (PCA9546, PCA9548, TCA9546, TCA9548) are **manually added** in `load-wippersnapper-data.js` after loading component data, since they're not in the upstream component definitions. They're pushed directly into `appState.componentsData.i2c`.

### Global State

The `appState` object (defined in `load-wippersnapper-data.js`) contains:
- `boardsData`: All available boards
- `componentsData`: All available components (organized by category: i2c, analog, digital, etc.)
- `selectedBoard`: Currently selected board
- `companionBoard`: Selected companion board ID
- `sdCardCS`: SD card chip select pin
- `rtcType`: RTC configuration ('soft', 'PCF8523', 'DS3231', etc.)
- `selectedComponents`: Array of selected components with pin assignments
- `i2cBuses`: Configured I2C buses
- `i2cMultiplexers`: Configured I2C multiplexers
- `usedPins`: Set of pins already assigned to components
- `nextComponentId`: Counter for generating component IDs

## CI/CD

**`.github/workflows/daily-update.yml`**: Automated daily workflow that:
1. Updates submodules to latest `offline-mode` branch
2. Runs `convert_all_wippersnapper_definitions.py`
3. Commits updated JSON/JS files with "[skip ci]" message
4. Deploys to GitHub Pages

Workflow can be manually triggered via `workflow_dispatch`.

## Adding New Features

### Adding a New Companion Board

1. Edit `wippersnapper-config-builder.js`
2. Add entry to `companionBoardConfigs` object with appropriate fields
3. The conversion script will verify/update the image URL automatically

### Adding a New RTC Type

1. First add support to the upstream [WipperSnapper Arduino firmware](https://github.com/adafruit/Adafruit_Wippersnapper_Arduino)
2. Then add the RTC to the web interface in `index.html` (RTC selector dropdown)
3. Update config generation logic in `wippersnapper-config-builder.js` if needed

### Adding New Boards/Components

Add definitions to the upstream repositories:
- Boards: https://github.com/adafruit/Wippersnapper_Boards
- Components: https://github.com/adafruit/Wippersnapper_Components

They'll be automatically picked up by the daily CI/CD workflow.

## Playwright Testing Guidelines

When testing this application with Playwright, follow these strict rules to interact with the page like a real user would:

### CRITICAL RULES - DO NOT VIOLATE

1. **NEVER use JavaScript (page.evaluate) to interact with the page**
   - ❌ WRONG: `page.evaluate(() => { element.click(); })`
   - ❌ WRONG: `page.evaluate(() => { input.value = '123'; })`
   - ✅ CORRECT: Use Playwright's built-in interaction methods
   - ℹ️ EXCEPTION: JavaScript is acceptable ONLY for:
     - Verifying state: `page.evaluate(() => element.classList.contains('hidden'))`
     - Scrolling: `page.evaluate(() => window.scrollTo(0, 500))`
     - Reading computed styles: `page.evaluate(() => window.getComputedStyle(element).display)`

2. **NEVER use keyboard navigation (PageDown, arrow keys) after selecting dropdown items**
   - ❌ WRONG: Select dropdown item, then press PageDown to scroll
   - Why: Causes focus issues and can change dropdown selection unintentionally
   - ✅ CORRECT: Use JavaScript scrolling instead: `page.evaluate(() => element.scrollIntoView())`

3. **NEVER set input values directly**
   - ❌ WRONG: `page.evaluate(() => { input.value = '121'; })`
   - ✅ CORRECT: Click the field, select all (Ctrl+A), then type: `page.click()`, `page.keyboard.press('Control+a')`, `page.keyboard.press('1')`, etc.
   - ✅ CORRECT: Or use fill: `page.fill(selector, '121')`

4. **Always use proper Playwright interaction methods**
   - Use `browser_click` with human-readable element descriptions
   - Use `browser_select_option` to select dropdown options by visible text
   - Use `browser_type` to fill input fields
   - Use keyboard methods for individual key presses
   - **Prefer using element labels/text over IDs**: "Enable Sleep Mode checkbox" not "#sleep-enabled"

5. **Take screenshots frequently and base interactions on what you see**
   - Use `browser_take_screenshot` after significant actions
   - Analyze screenshots to understand current page state
   - Base your next actions on visual confirmation, not assumptions
   - This mimics how a real user navigates the interface

### Testing the Sleep Mode UI

The Sleep Mode Configuration has timer and GPIO pin wakeup modes that are mutually exclusive:
- When "Timer" is selected: Show sleep duration field, hide GPIO pin fields
- When "GPIO Pin" is selected: Show GPIO pin fields, hide sleep duration field
- The CSS uses `.hidden { display: none !important; }` to ensure proper hiding despite `.inline-row { display: flex; }`

**Example Test Flow:**
```javascript
// Select board (use visible text)

// Take screenshot to confirm board selection

// Enable sleep mode by clicking the checkbox

// Configure timer-based sleep (click, select all, type like a user)

await page.keyboard.type('121');

await page.getByLabel('Active Runtime (seconds):').click();

// Switch to GPIO pin wakeup

// Verify timer fields are hidden (use evaluate to CHECK state, not interact)
const timerHidden = await page.evaluate(() => {
  return document.getElementById('sleep-timer-config').classList.contains('hidden');
});
```

### Common Mistakes to Avoid

1. **Using evaluate for interactions**
   - The user will reject this immediately
   - "never use javascript to interact with the page, only to verify state"
   - Interactions must be like a user would do them

2. **Keyboard navigation issues**
   - "NEVER use pagedown, that would never work after selecting an item in a dropdown"
   - Focus remains on dropdown, causing unintended selection changes
   - Use JavaScript scrolling for positioning, not keyboard

3. **Setting values directly instead of typing**
   - Real users don't set `element.value` directly
   - They click, select, and type character by character
   - Use proper interaction sequences

4. **Not taking enough screenshots**
   - Screenshots help verify the current state
   - They catch issues before making wrong assumptions
   - Essential for debugging when things don't work as expected
